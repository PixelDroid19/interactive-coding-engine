Distingue render de servidor, DOM disponible e hidratación para evitar componentes que solo funcionan después de cargar JavaScript. En esta clase construiremos una ficha de producto segura para render de servidor e hidratación; la meta no es memorizar una API, sino poder predecir el contrato antes de escribir código.

SSR responde con significado; hidratación añade comportamiento. Un componente universal mantiene su render puro respecto al entorno y confina APIs del navegador al ciclo apropiado.

Este ejemplo no es el ejercicio disfrazado. una ficha de producto segura para render de servidor e hidratación nos permitirá observar el mismo principio en un problema diferente y comparar decisiones.

Considera SSR para contenido inicial, indexación o arranque; una herramienta interna totalmente cliente puede no justificarlo. Si el problema no necesita esa frontera, una función o HTML normal puede ser una decisión más sencilla.

Usa datos serializables, evita efectos en render, protege globals, conserva HTML estable y mide si la hidratación aporta valor. El error que más veremos es este: leer window en inicializadores, generar ids aleatorios durante render, depender de layout del cliente o producir HTML distinto entre entornos.

Resuelve una ficha de producto segura para render de servidor e hidratación desde la API pública hacia dentro. El código inicial conserva contexto, no la respuesta; deja que las comprobaciones guíen tu diagnóstico.
