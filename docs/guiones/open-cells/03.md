Anatomía de un proyecto Cells. Recorre un scaffold completo antes de editarlo para saber qué archivo responde a cada pregunta.

Abrimos package.json. Este archivo declara identidad, entradas, dependencias y comandos que consumen las herramientas. Observa su entrada y busca qué otro archivo lo consume.

Ahora construimos package.json: type module permite usar import y export. exports señala la entrada pública; cells.entry señala el bootstrap de una app. Los scripts nombran operaciones reales de desarrollo, pruebas, locales y build.

Abrimos index.js. Este archivo expone la clase sin registrar efectos globales. Observa su entrada y busca qué otro archivo lo consume.

Ahora construimos index.js: exportamos la clase desde src. Este archivo no registra el tag: así una prueba o un consumidor puede importar la clase sin provocar un efecto global.

Abrimos academy-learning-card.js. Este archivo registra el tag público que una aplicación puede instanciar. Observa su entrada y busca qué otro archivo lo consume.

Ahora construimos academy-learning-card.js: importamos el polyfill del registro scoped, importamos la clase y registramos únicamente el tag público si todavía no existe.

Abrimos src/academy-learning-card.js. Este archivo implementa propiedades, render, dependencias scoped y eventos del componente. Observa su entrada y busca qué otro archivo lo consume.

Abrimos custom-elements.json. Este archivo describe la API para herramientas sin ejecutar el módulo. Observa su entrada y busca qué otro archivo lo consume.

Ejecutamos el proyecto después de conectar sus archivos. La evidencia que buscamos es esta: La demo debe importar e instanciar el componente como lo haría otra aplicación. Las pruebas también actúan desde fuera: asignan propiedades, esperan updateComplete, interactúan y escuchan eventos. Ambas superficies detectan contratos que una revisión del archivo fuente puede pasar por alto.

Antes de practicar, contrasta el resultado con este error frecuente: Los catálogos EN y ES deben contener las mismas claves y placeholders. Una traducción faltante no debe convertirse silenciosamente en una cadena vacía: el diagnóstico visible ayuda a corregir el catálogo antes de publicar. Un error frecuente consiste en cambiar varias fronteras a la vez; conserva una predicción y comprueba una sola causa antes de continuar.
