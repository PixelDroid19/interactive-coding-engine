Bridge entre la aplicación web y el shell nativo. Bridge separa las páginas Cells del contenedor móvil: el shell puede comunicar ciclo de vida, sesión o capacidades, pero los componentes reciben contratos web serializables.

Abrimos app/bridge/native-adapter.js. Este archivo valida mensajes del shell y los traduce a navegación o canales internos. Observa su entrada y busca qué otro archivo lo consume.

Abrimos app/scripts/channels.js. Este archivo nombra contratos de comunicación de larga distancia. Observa su entrada y busca qué otro archivo lo consume.

Abrimos app/pages/academy-home-page/academy-home-page.js. Este archivo coordina componentes, ciclo de página y navegación. Observa su entrada y busca qué otro archivo lo consume.

Ahora construimos app/pages/academy-home-page/academy-home-page.js: PageMixin aporta navegación y canales; ScopedElementsMixin resuelve la tarjeta. onPageEnter adquiere recursos, onPageLeave los libera y render conserva UI declarativa.

Abrimos app/scripts/app-routes.js. Este archivo relaciona URL, nombre estable, tag de página y carga lazy. Observa su entrada y busca qué otro archivo lo consume.

Ejecutamos el proyecto después de conectar sus archivos. La evidencia que buscamos es esta: Un adaptador aislado valida cada mensaje, publica estados internos y mantiene fuera de páginas y componentes cualquier objeto específico de la plataforma nativa.

Antes de practicar, contrasta el resultado con este error frecuente: Llamar APIs nativas desde cada página hace imposible probar o sustituir el shell; dibuja una única frontera y comprueba mensajes válidos, incompletos y desconocidos.

La lectura siguiente abre un laboratorio de proyecto para Bridge entre la aplicación web y el shell nativo. Allí corregirás archivos reales, construirás la vista previa y ejecutarás contratos sin recibir una solución copiada.
