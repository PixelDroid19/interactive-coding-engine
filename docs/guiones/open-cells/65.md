Build con configuración de producción. El build de producción fija entorno, resuelve rutas y elimina capacidades de depuración sin cambiar comportamiento público. Hoy seguiremos el recorrido test/unit/app.test.js → app/data/academy-product-data-manager.js → app/scripts/app-routes.js → package.json. Para entender Build con configuración de producción, identificaremos quién posee cada dato, quién consume su salida y qué resultado observable confirma el contrato.

La primera parada está en test/unit/app.test.js. Este archivo comprueba la historia vertical desde rutas y páginas hasta datos. Antes de tocarlo en Build con configuración de producción, localiza su salida pública y predice quién dependerá de ella.

Ahora sí editamos test/unit/app.test.js. Las pruebas conectan rutas, páginas y data manager con valores variables; además verifican cleanup y respuestas antiguas. Después lo contrastaremos con app/data/academy-product-data-manager.js para verificar el contrato desde otro archivo.

El siguiente enlace aparece en app/data/academy-product-data-manager.js. Este archivo posee petición, estados, carreras y cancelación. Revisa qué recibe de test/unit/app.test.js y qué deja preparado para app/scripts/app-routes.js. En Build con configuración de producción, app/data/academy-product-data-manager.js queda intacto para comprobar el contrato desde fuera.

Ahora pasamos a app/scripts/app-routes.js. Este archivo relaciona URL, nombre estable, tag de página y carga lazy. Revisa qué recibe de app/data/academy-product-data-manager.js y qué deja preparado para package.json. app/scripts/app-routes.js actúa como consumidor del cambio y no necesita otra edición en este paso.

Cerramos el recorrido en package.json. Este archivo declara identidad, entradas, dependencias y comandos que consumen las herramientas. Compáralo con app/scripts/app-routes.js: deben colaborar sin duplicar responsabilidades. Solo inspeccionamos package.json; cambiarlo también ocultaría la causa del resultado.

Con los archivos enlazados, observa este contrato: El artefacto arranca desde cero, carga páginas lazy y no contiene secretos ni URLs de desarrollo. Si el preview contradice tu predicción sobre Build con configuración de producción, vuelve al último archivo editado y sigue su salida hasta el consumidor.

Haz una última predicción sobre este error frecuente: Un build exitoso puede estar mal configurado; inspecciona el artefacto y ejecuta un smoke real. En Build con configuración de producción, propón una causa, cambia una sola frontera y usa el preview o las pruebas para refutarla.
