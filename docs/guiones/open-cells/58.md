Transiciones de una petición. Una petición es una máquina de estados: idle → loading → success, empty o error, con retry y cancelación posibles. Hoy seguiremos el recorrido app/data/academy-product-data-manager.js → app/pages/academy-home-page/academy-home-page.js → app/components/academy-product-card/academy-product-card.js → package.json. Para entender Transiciones de una petición, identificaremos quién posee cada dato, quién consume su salida y qué resultado observable confirma el contrato.

Nuestro punto de partida es app/data/academy-product-data-manager.js. Este archivo posee petición, estados, carreras y cancelación. Antes de tocarlo en Transiciones de una petición, localiza su salida pública y predice quién dependerá de ella.

Este es el archivo que modificaremos: app/data/academy-product-data-manager.js. RequestId identifica la petición vigente, AbortController permite cancelarla y emit diferencia loading, success, empty y error. Después lo contrastaremos con app/pages/academy-home-page/academy-home-page.js para verificar el contrato desde otro archivo.

Ahora pasamos a app/pages/academy-home-page/academy-home-page.js. Este archivo coordina componentes, ciclo de página y navegación. Revisa qué recibe de app/data/academy-product-data-manager.js y qué deja preparado para app/components/academy-product-card/academy-product-card.js.

Aquí hacemos el cambio principal en app/pages/academy-home-page/academy-home-page.js. PageMixin aporta navegación y canales; ScopedElementsMixin resuelve la tarjeta. onPageEnter adquiere recursos, onPageLeave los libera y render conserva UI declarativa. Después lo contrastaremos con app/components/academy-product-card/academy-product-card.js para verificar el contrato desde otro archivo.

Después abrimos app/components/academy-product-card/academy-product-card.js. Este archivo encapsula presentación y devuelve una intención mediante evento. Revisa qué recibe de app/pages/academy-home-page/academy-home-page.js y qué deja preparado para package.json.

Vamos a completar app/components/academy-product-card/academy-product-card.js. La tarjeta recibe product por propiedad y emite select. No importa rutas ni canales porque esa coordinación pertenece a la página. Después lo contrastaremos con package.json para verificar el contrato desde otro archivo.

La última parada es package.json. Este archivo declara identidad, entradas, dependencias y comandos que consumen las herramientas. Compáralo con app/components/academy-product-card/academy-product-card.js: deben colaborar sin duplicar responsabilidades. package.json actúa como consumidor del cambio y no necesita otra edición en este paso.

Ya está conectado el recorrido. La comprobación importante es esta: Cada transición limpia datos incompatibles y produce una salida observable única. Si el preview contradice tu predicción sobre Transiciones de una petición, vuelve al último archivo editado y sigue su salida hasta el consumidor.

Ahora piensa en el caso que suele romper este contrato: Actualizar error sin retirar loading deja dos verdades; usa una tabla de estado y revisa cada salida. En Transiciones de una petición, propón una causa, cambia una sola frontera y usa el preview o las pruebas para refutarla.
