Locales de aplicación. El shell decide idioma y las páginas consumen el mismo contrato de recursos sin duplicar catálogos por componente. Hoy seguiremos el recorrido test/unit/app.test.js → app/pages/academy-home-page/academy-home-page.js → app/components/academy-product-card/academy-product-card.js → package.json. Para entender Locales de aplicación, identificaremos quién posee cada dato, quién consume su salida y qué resultado observable confirma el contrato.

Nuestro punto de partida es test/unit/app.test.js. Este archivo comprueba la historia vertical desde rutas y páginas hasta datos. Antes de tocarlo en Locales de aplicación, localiza su salida pública y predice quién dependerá de ella.

Vamos a completar test/unit/app.test.js. Las pruebas conectan rutas, páginas y data manager con valores variables; además verifican cleanup y respuestas antiguas. Después lo contrastaremos con app/pages/academy-home-page/academy-home-page.js para verificar el contrato desde otro archivo.

Seguimos en app/pages/academy-home-page/academy-home-page.js. Este archivo coordina componentes, ciclo de página y navegación. Revisa qué recibe de test/unit/app.test.js y qué deja preparado para app/components/academy-product-card/academy-product-card.js. Solo inspeccionamos app/pages/academy-home-page/academy-home-page.js; cambiarlo también ocultaría la causa del resultado.

El siguiente enlace aparece en app/components/academy-product-card/academy-product-card.js. Este archivo encapsula presentación y devuelve una intención mediante evento. Revisa qué recibe de app/pages/academy-home-page/academy-home-page.js y qué deja preparado para package.json. En Locales de aplicación, app/components/academy-product-card/academy-product-card.js queda intacto para comprobar el contrato desde fuera.

La última parada es package.json. Este archivo declara identidad, entradas, dependencias y comandos que consumen las herramientas. Compáralo con app/components/academy-product-card/academy-product-card.js: deben colaborar sin duplicar responsabilidades. package.json actúa como consumidor del cambio y no necesita otra edición en este paso.

Ya está conectado el recorrido. La comprobación importante es esta: Cambio de idioma actualiza la página activa y una página lazy carga su texto correcto al entrar después. Si el preview contradice tu predicción sobre Locales de aplicación, vuelve al último archivo editado y sigue su salida hasta el consumidor.

Ahora piensa en el caso que suele romper este contrato: Precargar solo la página inicial deja huecos al navegar; prueba una ruta que todavía no se había importado. En Locales de aplicación, propón una causa, cambia una sola frontera y usa el preview o las pruebas para refutarla.

A continuación podrás repasar el modelo con calma sobre Locales de aplicación. Después, el proyecto de Locales de aplicación se abrirá completo para que experimentes y compares soluciones equivalentes sin recibir una línea para copiar.
