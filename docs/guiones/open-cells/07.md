Anatomía del scaffold de componente. El scaffold es un mapa de responsabilidades, no una carpeta ceremonial: entrada pública, demo, locales, pruebas y documentación tienen consumidores distintos.

En Anatomía del scaffold de componente, este archivo es la frontera que vamos a observar. No trabaja solo: Puedes señalar qué archivo modificar para cambiar API, traducción, demo o metadata sin recorrer todo el proyecto.

Haz que el contrato visible respete disabled y conserve loading, empty, error o success. Una entrada desconocida debe producir un estado seguro. Primero aislamos esa decisión en estadoVisible07; después cambiaremos varias entradas para comprobar que no depende de un ejemplo fijo.

La demostración hace visible este modelo: propiedad pública → estado interno → render e interacción. Sigue la entrada que cambia y localiza el caso que debe permanecer ausente, bloqueado o rechazado.

Ahora contrasta el resultado con el error frecuente. Copiar código dentro de la demo en vez de consumir la entrada pública oculta errores de empaquetado; comprueba siempre el import que usaría otra aplicación.

Te devuelvo el punto de partida de Anatomía del scaffold de componente. Predice las tres comprobaciones de estadoVisible07 antes de escribir y corrige una sola causa cada vez.

Después del reto de Anatomía del scaffold de componente, la lectura ampliará el porqué, el razonamiento reconstruirá el flujo y la depuración te pedirá transferirlo a otro programa.
